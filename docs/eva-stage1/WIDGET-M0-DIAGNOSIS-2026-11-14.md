# M0 — диагностика зависания чата VLICO

14 ноября 2026 года. Область — пункт 8 [плана доработок по обратной связи Владлена](VLADLEN-WIDGET-SALES-PLAN-2026-11-14.md). Статус M0 — завершён. Есть воспроизводимый сбой интерфейса при ошибке транспорта и повторяемая диагностика для M1. Сетевой ответ во время исходного случая Владлена неизвестен.

## Среда и ограничения

- Локальная исходная версия `8c8b31b`, Docker Compose `localhost:8000`. Web и PostgreSQL достигли состояния healthy, `manage.py check` прошёл. Локальная загрузка скрипта виджета через Django вернула HTTP 502 за 12,06 с. Прямой HTTPS из контейнера отдельно остановился на TLS handshake. Windows-хост получил HTTP 200 от Eva. Это отдельный сбой локального доступа, возникающий ещё до запуска чата.
- На рабочем сайте зафиксированы реально отданные адаптер `/static/eva-widget.16786b896d33.js`, скрипт виджета через домен VLICO и HTTP 200 при чтении его настроек. Диалоги — две отдельные сессии Chromium. Мобильная проверка в эмуляции 390 px. Профиль реального телефона и конкретный VPN-маршрут остаются для M1/M6.
- Перед живой проверкой через API подтверждено, что семь задач рассылок выключены, виджет подключён к «VLICO | Входящие клиенты», а каналы уведомлений у пользователей Eva отсутствуют. Для прогона использованы только вымышленные адреса и зарезервированные фиктивные номера. Рабочие настройки не менялись. Созданы две синтетические беседы, каждая помечена текстом `VLICO_TEST_M0_*` и связана с одной карточкой. Телефоны, токены, идентификаторы контактов и содержимое переписки в отчёт не включены.

## Живой сценарий на SpaceWeb

Старт 10:54:51 UTC на компьютере, затем 10:55:58 UTC в эмуляции телефона. На компьютере запрос «замер сегодня», адрес и телефон отправлены тремя сообщениями. На мобильном все три условия отправлены одним сообщением. В обоих случаях отправлен следующий вопрос о продолжении переписки. Запросы содержали указание о тестовом характере и запрет на выезд. Задержки ниже отсчитываются от нажатия «Отправить». Сохранение в Eva вычислено от отметки нажатия в браузере до времени `createdAt` сообщения в API, поэтому эти оценки зависят от синхронизации часов. Появление ответа измерено в браузере.

| Сценарий | POST, HTTP | Сообщение в Eva | Ответ в чате |
|---|---|---|---|
| Компьютер, запрос замера | 200, 1,18 с | ≈1,02 с | 7,87 с |
| Компьютер, адрес | 200, 1,09 с | ≈1,00 с | 10,43 с |
| Компьютер, телефон | 200, 2,93 с | ≈1,60 с | 8,86 с |
| Компьютер, следующий вопрос | 200 | ≈0,86 с | 11,45 с |
| Мобильный, запрос с адресом и телефоном | 200, 1,18 с | ≈0,99 с | 17,16 с |
| Мобильный, следующий вопрос | 200, 0,80 с | ≈0,94 с | 8,37 с |

Адрес и телефон найдены в истории Eva в обоих случаях. История содержит 4 пользовательских и 4 ответных сообщения на компьютере, 2 и 2 на мобильном. После ответов поле ввода было доступно. Для первого мобильного ответа разница между сохранением реплики Артема в Eva и отображением в браузере составила около 6,6 с. В тестах переход Socket.IO на WebSocket закончился ошибкой рукопожатия с HTTP 404. Сообщения и ответы дошли по polling. В отдельной проверке без отправки сообщения после трёхсекундного отключения сети новое соединение polling вернуло HTTP 200 через 1,87 с после восстановления сети.

У каждой беседы одна карточка в основной входящей воронке, исполнитель Артем. Карточки созданы примерно через 0,21 и 0,19 с после первого сообщения в истории Eva. При чтении контактов поле телефона было пустым, а ожидаемые атрибуты заявки отсутствовали. При проверке через 8 мин 54 с для компьютера и 7 мин 48 с для мобильного обе карточки оставались в «Новая заявка». Тест проверяет сохранность текста с фиктивным номером и адресом в истории. Для проверки распознавания и заполнения полей при обычных входных данных нужен отдельный контрольный сценарий M2. Канала доставки уведомления нет, поэтому время уведомления измерить невозможно.

## Контролируемое воспроизведение таймаута

[Диагностический сценарий Playwright](../../scripts/diagnose-eva-widget-send.js) выполняется в изолированной сессии. Он загружает текущий виджет, перехватывает один POST, отвечает пустым HTTP 502 через 12 секунд и блокирует остальную запись и транспорт сообщений. Синтетическая реплика в Eva не отправляется. Код 502 и задержка соответствуют тому, что пользователь может получить от [прокси](../../backend/core/eva_widget_relay.py) при ошибке HTTPS на пути к Eva.

```powershell
playwright-cli -s=vlico-m0 open https://vlico39.ru/
playwright-cli -s=vlico-m0 run-code --filename=./scripts/diagnose-eva-widget-send.js
playwright-cli -s=vlico-m0 close
```

Наблюдаемый результат. В течение ожидания поле и кнопка заблокированы. Текст остаётся в поле, исходящего сообщения и видимого статуса ошибки нет. После 502 примерно через 12,04 с поле и кнопка снова доступны, черновик сохранён. Чат всё ещё не объясняет, что сообщение не принято. Это воспроизводимый механизм ощущения зависания и контрольный сценарий для M1. Живые контрольные отправки прошли. Связь этого механизма с исходным случаем Владлена остаётся гипотезой, потому что сетевой трассы того сеанса нет.

## Что передаём дальше

- **M1.** На том же сценарии проверить отдельно ожидание приёма сообщения и ожидание ответа Артема. После 502 клиент видит понятный статус, черновик сохранён, автоматического повторного POST нет. Для потерянного ответа после возможной доставки сначала сверить историю, когда это позволяет транспорт.
- **M2.** Повторно прочитать стадию, проверять перенос согласованных данных из истории в карточку, назначение ответственного и получение уведомления на согласованном тестовом канале. Сохранить ручное одобрение замера и провести проверку без назначения реального выезда.
