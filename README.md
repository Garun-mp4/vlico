# VLICO

Локальная серверная версия сайта: Django 5.2 LTS, PostgreSQL и Docker Compose. Для виртуального хостинга SpaceWeb с mod_wsgi/Python 3.8 предусмотрен отдельный файл совместимых зависимостей `requirements-spaceweb.txt`. Работают кабинет портфолио, серверные заявки, числовой калькулятор с версиями тарифов и независимые уведомления в Telegram и по электронной почте.

## Запуск на Windows

1. Запустить Docker Desktop и проверить доступность Docker командой `docker info`.
2. Из корня проекта: `powershell -ExecutionPolicy Bypass -File scripts/init-local.ps1`. Скрипт создаёт `.env` со случайными секретами и сохраняет существующий файл без изменений.
3. `docker compose up -d --build --wait`
4. Открыть http://localhost:8000/. Диагностика: `docker compose ps`, `docker compose logs --tail=50 web`, http://localhost:8000/health/.

По умолчанию порт доступен только на loopback компьютера (`WEB_BIND_ADDRESS=127.0.0.1`). Для проверки с телефона в той же Wi-Fi-сети установить в приватном `.env` `WEB_BIND_ADDRESS=0.0.0.0`, добавить текущий LAN IPv4 компьютера в `DJANGO_ALLOWED_HOSTS`, а `http://<LAN-IP>:8000` — в `DJANGO_CSRF_TRUSTED_ORIGINS`. Применить: `docker compose up -d --no-build --wait`. В брандмауэре разрешить входящий TCP 8000 только с локальной подсети на Wi-Fi-интерфейсе. На телефоне открыть `http://<LAN-IP>:8000/` (именно HTTP); телефон и компьютер должны быть в одной сети без изоляции клиентов. При смене IP обновить окружение и правило. Для возврата к доступу только с компьютера установить `WEB_BIND_ADDRESS=127.0.0.1` и повторить команду запуска. БД наружу не публикуется. Если порт занят, изменить WEB_PORT и соответствующие доверенные origins в `.env`.

Миграции и collectstatic выполняются перед стартом Gunicorn. После правки кода выполнить `docker compose up -d --build --wait`. После правки окружения пересоздать контейнер (`up -d`), одного restart недостаточно.

## Перенос на VPS

1. Подключиться по SSH (`ssh -p 22 deploy@SERVER_IP`, подставив свои порт, пользователя и IP). На Linux-сервере нужны Docker Engine с Compose и доступ к коду из ветки `main`.
2. Создать серверный `.env` по `.env.example` с отдельными секретами. Для публичного запуска задать `APP_ENV=production`, HTTPS-адрес в `SITE_URL`, домен в `DJANGO_ALLOWED_HOSTS` и HTTPS-адрес в `DJANGO_CSRF_TRUSTED_ORIGINS`. Если обратный прокси работает на хосте, оставить `WEB_BIND_ADDRESS=127.0.0.1`.
3. Для переноса текущего сайта подготовить дамп PostgreSQL и копии обоих медиатомов, `public_media` и `private_media`. Передать их по SSH и восстановить вместе до открытия доступа. Дамп содержит заявки, а приватный том может содержать вложения. Хранить и передавать эти копии как закрытые данные.
4. После подготовки конфигурации и восстановления данных запустить `docker compose up -d --build --wait` и проверить `docker compose ps`. Настроить DNS A-запись на публичный IPv4 сервера и обратный прокси с HTTPS. Проверить по домену `/health/`, вход в кабинет, каталог и загрузку фотографий.
5. При переносе очереди заявок оставить `TELEGRAM_DELIVERY_ENABLED=false` на новом сервере до переключения. Включить отправку после остановки старого процесса доставки и проверки статусов очереди.

## Виртуальный хостинг SpaceWeb

Для Apache/mod_wsgi с Python 3.8 используется `requirements-spaceweb.txt`; эта конфигурация старше локального профиля и выбрана для совместимости с тарифом. Хранить `.env` в корне приложения вне `public_html`: WSGI загружает его перед стартом Django. При необходимости путь к окружению можно отдельно задать в `VLICO_ENV_FILE`; без этого используется `.env` в корне приложения. Приложение, виртуальное окружение, база и медиа находятся отдельно от корня сайта. После установки зависимостей выполнить `manage.py migrate` и `manage.py collectstatic`. Для доставки заявок создать cron-задачу на `scripts/deliver-leads-once.sh` с интервалом в одну минуту; для отдельного production-окружения передать тот же `VLICO_ENV_FILE` этой задаче. Для Mail.ru SMTP включить `EMAIL_DELIVERY_ENABLED`, указать `LEAD_NOTIFICATION_EMAIL`, `EMAIL_HOST_USER`, `DEFAULT_FROM_EMAIL`, сервер `smtp.mail.ru`, порт 465 и SSL; пароль внешнего приложения хранить только в закрытом `.env`.

Если на виртуальном хостинге доступен Python CGI, но нельзя включить mod_wsgi, можно запускать WSGI-приложение через CGI-адаптер `scripts/spaceweb-cgi-runner.py`. Скопировать адаптер и обычный `wsgi.py` в `public_html`, установить адаптеру права на исполнение (`chmod 755 spaceweb-cgi-runner.py`) и использовать правила Apache:

```apache
AddDefaultCharset utf-8
AddHandler cgi-script .py
RewriteEngine On
RewriteCond %{REQUEST_URI} !^/spaceweb-cgi-runner\.py
RewriteCond %{REQUEST_FILENAME} !-f
RewriteRule ^(.*)$ /spaceweb-cgi-runner.py/$1 [QSA,L]
```

CGI запускает отдельный процесс Python на каждый запрос. Этот способ проверен на тестовом сайте SpaceWeb; для сайтов с высокой нагрузкой предпочтителен mod_wsgi или VPS. Собрать статику командой `collectstatic`; при настройке `WhiteNoise` запросы к статике тоже могут обрабатываться через CGI. Если HTTPS завершается на доверенном прокси, который перезаписывает входящий `X-Forwarded-Proto`, в `.env` можно включить `TRUST_X_FORWARDED_PROTO=true`, чтобы Django распознавал HTTPS.

Python 3.8 и Django 4.2 больше не получают обычные обновления безопасности. Этот профиль подходит для запуска на текущем тарифе, но для долгосрочного публичного размещения предпочтительна поддерживаемая версия Python на VPS.

## Проверки

```powershell
docker compose exec web python manage.py check
docker compose exec web python manage.py makemigrations --check --dry-run
docker compose exec web python manage.py test core
docker compose exec web python manage.py showmigrations
```

Новые миграции создаются в исходниках и коммитятся. Создание миграции внутри контейнера без копирования в `backend/core/migrations/` потеряет её при пересборке. Для дальнейшей разработки можно использовать временный bind mount backend; текущий образ намеренно воспроизводимый, без привязки к рабочей папке.

## Данные и безопасность

- `database`: PostgreSQL, включая контакты; `public_media`: подготовленные фото портфолио; `private_media`: исторические вложения заявок и приватные исходные копии фото. Все три named volumes сохраняются при пересоздании контейнеров.
- Не использовать `docker compose down --volumes`: это удалит данные. Остановка: `docker compose stop`; повторный запуск: `docker compose up -d --wait`.
- Volume не является резервной копией. До production требуется отдельное копирование БД/медиа и проверка восстановления (milestone 5).
- Фото опубликованных проектов доступны через проверяемые серверные маршруты. Планировки заявок хранятся приватно; скачивание доступно сотрудникам с отдельным правом, публичного URL нет.
- `.env` исключён из Git и Docker build context. Токен Telegram читается сервером из окружения, не передаётся в браузер и не выводится в журналы ошибок транспорта.
- Не публиковать вывод `docker compose config` и окружение контейнеров: они содержат секреты. Для проверки синтаксиса использовать `docker compose config --quiet`.
- APP_ENV: local/preview/production. DEBUG выключен во всех средах. Preview и local закрыты от индексации. Production требует HTTPS, отдельные секреты, разрешённые hosts/origins и настройки reverse proxy; текущий Compose предназначен для локального запуска.
- SITE_INDEXABLE пока не включать: SEO подготовлено, индексация включается только при согласованном запуске production в milestone 5.

## Структура

- `backend/`: Django, серверный шаблон главной, модели, миграции, проверки.
- `wireframe/assets`, `wireframe/styles.css`, `wireframe/main.js`: общие подготовленные ресурсы; Django обслуживает их через WhiteNoise с хешированными именами.
- `wireframe/index.html`: сохранённая статическая версия прежнего Vercel-preview. Новый HTML меняется в `backend/templates/site/home.html`; синхронизация legacy preview не является production-публикацией.
- `from-client/` и `фото-работ/`: исходники клиента, не входят в Docker image и не раздаются сервером.
- `docs/architecture.md`: модель данных, границы этапа и план следующих интеграций.

Существующий Vercel-preview продолжает публиковать `wireframe/`. Не менять его root directory на корень репозитория. Push в Git не разворачивает локальный Compose на сервере клиента.

## Кабинет и начальные данные

Кнопка «Выйти» в кабинете запрашивает подтверждение.

Кабинет доступен по адресу http://localhost:8000/cabinet/. Для создания редактора задайте `VLICO_EDITOR_PASSWORD` в приватном `.env`, пересоздайте сервис `web` и выполните:

```powershell
docker compose exec web python manage.py create_editor --username vlico
```

Команда не меняет существующий аккаунт и не печатает пароль. Смена пароля: `docker compose exec web python manage.py changepassword vlico`. Начальные доступы не предназначены для переноса в production без смены.

Работа редактора: нажмите «Новый проект» → введите название → создайте черновик (адрес страницы сформируется автоматически, если оставить его пустым) → добавьте фото → заполните описание и категории → сохраните сведения → откройте предпросмотр → подтвердите проверку сведений → опубликуйте. Поиск по названию/локации, категории, статусы и сортировка списка работают совместно без перезагрузки страницы. Изменение контента опубликованного проекта становится видно сразу после сохранения. Снятие с публикации немедленно скрывает страницу и фотографии от гостей. Архив сохраняет материалы и позволяет восстановить черновик.

Публичный каталог: http://localhost:8000/projects/. Все опубликованные проекты доступны в каталоге. На главной показываются первые шесть: три колонки на компьютере, две на планшете, одна на телефоне. Порядок управляется полем «Порядок показа», отдельная галочка не нужна. Под превью находится ссылка на полный каталог. Тарифы и заявки редактируются в своих разделах кабинета.

`python manage.py seed_portfolio` создаёт подготовленные черновики и шесть направлений услуг без публикации и перезаписи существующих данных. Для импорта фотографий используется `--source-root` с доступной контейнеру папкой исходников, смонтированной read-only. Источники не нужно включать в Docker image. В текущую локальную БД фото уже импортированы. Реестр материалов: `docs/portfolio-materials.md`. Не все черновики подтверждены как отдельные объекты.

Плейсхолдеры недостающих данных отображаются в полях кабинета и защищённом предпросмотре; внутренние заметки не публикуются. Общий список работ и sitemap обновляются без деплоя.

## Подготовка фотографий

Первая ячейка галереи всегда является обложкой и выделена зелёной рамкой. В пустой галерее на её месте доступна кнопка «Добавить обложку», включая перетаскивание файлов. Перетаскивание фотографии на первое место, кнопки перемещения и команда «Сделать обложкой» меняют обложку вместе с порядком. Выбор обложки при загрузке или кадрировании также переносит снимок в начало. После удаления первой фотографии обложкой становится следующая. Миграция сохраняет прежние обложки, перемещая их на первое место.

Редактор открывается автоматически после выбора файлов. Отдельная кнопка загрузки остаётся только в запасном варианте без JavaScript. Если сведения проекта не сохранены, сначала сохраните их, затем заново выберите фотографии.

Удаление проекта доступно в меню «···» списка и в панели публикации. Страница подтверждения проверяет актуальность проекта и право `core.delete_project`. Удаляются проект, фотографии, миниатюры и приватные исходники; связанные обращения и история доставки сохраняются. Для временного скрытия используйте архив. Опубликованный проект нельзя сохранить с пустым описанием решения.

Выберите до 8 файлов одновременно. Редактор последовательно открывает каждую фотографию: формат 4:3, 16:9, 1:1, 3:4, 9:16 или исходные пропорции, масштаб и положение, поворот, режим «Сохранить целиком с полями», подпись, описание, раздел результата/монтажа и обложка. Формат сохраняется отдельно для каждой фотографии и восстанавливается при повторном редактировании. Сохранение сразу добавляет фото в проект; затем открывается следующее. «Пропустить» не загружает текущий файл. Закрытие сохраняет уже добавленные фотографии, но не загружает остальные.

Для подписи и описания нажмите миниатюру: откроется боковая панель. Формат, кадрирование и поворот доступны в меню «···» у фотографии. Порядок можно менять перетаскиванием или кнопками «Переместить выше/ниже» в меню. Настройки применяются на сервере к сохранённой исходной копии, поэтому кадр можно сбросить. Исходная копия подготовлена без EXIF, с длинной стороной до 2000px, хранится приватно. Оригиналы файлов клиента на диске не изменяются. Выбранный кадр применяется к публичному изображению и миниатюре. В карточках сетки новые кадры видны целиком в одинаковых рамках с полями при необходимости; в галерее проекта сохраняются выбранные пропорции. Для старых настроек редактора используется формат 4:3; существующие файлы автоматически не перекадрируются.

Повтор запроса при обрыве связи защищён ключом загрузки от дублирования. Изменения из устаревшей вкладки не перезаписывают новую редакцию. Сведения проекта сохраняются отдельной кнопкой, галерея — при выполнении действия. Если сведения ещё не сохранены, сначала сохраните их, затем открывайте редактор фото, публикацию или предпросмотр. Без JavaScript остаётся обычная пакетная загрузка.

Команда `reconcile_portfolio --source-root <папка>` переносит фото из старых общих черновиков в подтверждённые объекты и дополняет группы без дублирования. В локальной БД это уже выполнено: Леонова — 7 фото, Холмогоровка — 4 монтажных фото. Остальные материалы распределены по предварительным черновикам, непроверенные адреса не присвоены.

## Категории проектов

В кабинете можно отдельно управлять видимостью категории на сайте. Скрытые категории остаются доступными редактору и исчезают из публичного списка направлений и фильтра каталога.

Раздел «Категории» доступен из шапки кабинета. Базовые категории: теневые и парящие потолки, световые линии, магнитные треки, скрытые карнизы, тканевые потолки. Их можно добавлять, редактировать, упорядочивать и удалять. У проекта может быть несколько категорий; без категории он остаётся в общем списке. Категории независимы от будущих страниц услуг.

Удаление категории требует подтверждения и снимает только её связи с проектами. Проекты, фото, остальные категории и статус публикации сохраняются. Списки категорий и фильтры обновляются сразу, повторный запуск не восстанавливает удалённые категории. Изменения из устаревшей вкладки отклоняются.

На сайте категории отображаются в карточках и кейсе, в каталоге есть фильтры с числом опубликованных работ. Кабинет позволяет совместно фильтровать статус и категорию. Черновики и архивные работы остаются недоступными посетителям. После нажатия «Опубликовать» проект появляется в каталоге и sitemap без деплоя; на главной показываются первые шесть по порядку.

На главной фотографии внутри карточки проекта переключаются стрелками, перетаскиванием мышью или свайпом. Первой показывается выбранная в кабинете обложка, затем остальные снимки в сохранённом порядке. Доступны клавиши ←/→ и Home/End; автопрокрутки нет. Для одной фотографии переключатели скрыты. Клик по фотографии, названию или ссылке «Смотреть проект» открывает кейс. В полном каталоге сохраняются обычные карточки с обложками.

## Заявки, калькулятор и уведомления

В конце уведомления Telegram указаны источник и дата создания заявки в формате `ДД.ММ.ГГГГ`.

- `/calculator/`: предварительный серверный расчёт. Площадь × материал + периметр × одно выбранное примыкание + световые линии, треки, карнизы и световые точки. Если периметр неизвестен, сумма явно помечается неполной. Оборудование, электрика и дополнительные работы не включены.
- `/request/consultation/`, `/request/measurement/`, `/request/project/`, `/request/partner/`: общая обработка обращений; форма на главной тоже сохраняет настоящие заявки. CTA кейса передаёт выбранный проект. Страницы услуг и сотрудничества используют эти же формы, передают услугу или интерес «Сотрудничество».
- `/cabinet/leads/`: поиск, статусы «Новая / В работе / Закрыта / В архиве», контакт, комментарий, сохранённый расчёт, источник и приватные файлы. Статусы Telegram и электронной почты независимы от статуса обработки обращения.
- `/cabinet/rates/`: цены, названия позиций и совместимые единицы. Сохранение создаёт новую версию без деплоя. Старые суммы в заявках не пересчитываются; устаревшая форма предлагает проверить обновлённую цену.
- Публичные формы, включая квиз и обсуждение проекта, не принимают файлов. Сервер отклоняет любые вложения; общий предел запроса — 2 МБ. Контакт, комментарий, выбранные параметры и расчёт сохраняются как прежде. Вложения старых заявок остаются приватными и доступны уполномоченным сотрудникам; загрузка фотографий портфолио в кабинете сохраняется.
- Согласие обязательно. Форма защищена CSRF, подписанным ключом, honeypot и общим для workers лимитом 12 попыток за 15 минут с адреса. Повтор того же запроса возвращает сохранённую заявку; изменение данных с уже использованным ключом отклоняется.

Для уведомлений указать приватно в `.env` `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и `TELEGRAM_DELIVERY_ENABLED=true`. Получатель должен сначала открыть чат с ботом и нажать «Запустить». После изменения окружения выполнить `docker compose up -d --no-build --wait`: пересоздаются web и delivery. В новом окружении сначала собрать образ обычной командой запуска выше.

У заявок из форм и калькулятора разные обложки. Короткий текст входит в подпись к обложке, длинный приходит ответом на неё. Уведомление калькулятора показывает итог, уточнения, ответы по шагам и раскрываемую разбивку стоимости. Кнопка «Открыть заявку» ведёт в закрытую карточку на домене `SITE_URL`.

Сервис `delivery` использует тот же образ и PostgreSQL, без Redis. Заявка и запись очереди сохраняются одной транзакцией; ответ посетителю подтверждает сохранение. Подтверждённые Telegram части и файлы записываются отдельно, чтобы не повторять их после частичной ошибки. Временные отказы получают до 5 попыток. Если ответ потерян или процесс прервался во время отправки, требуется проверка Telegram и подтверждённый ручной повтор из заявки: Telegram не предоставляет нашему запросу ключа идемпотентности. При `chat not found` проверить аккаунт получателя и запуск бота.

Диагностика: `docker compose ps`, `docker compose logs --tail=30 delivery`, статусы в карточке заявки. Healthcheck delivery проверяет жизнь процесса, а не доступность Telegram. `TELEGRAM_DELIVERY_ENABLED=false` приостанавливает отправку, сохраняя заявки и очередь. Не публиковать конфигурацию с секретами.

UTM и источник первого перехода сохраняются в браузере до 30 дней; при недоступном localStorage используется текущая серверная сессия. Query-параметры контактов и лишние поля источника не сохраняются. Событие `vlico:lead-saved` содержит тип и идентификатор заявки для локальной защиты от дублей; в Метрику идентификатор не передаётся. В `Lead.context.consent` сохраняются редакция, SHA-256 и полный принятый текст. Если текст или реквизиты изменились после открытия формы, сервер требует обновить страницу. Согласие не предустановлено и оформлено отдельно от политики.

Проверки milestone 3 и реальная тестовая доставка описаны в `docs/milestone-3-validation.md`. Секреты и временные QA-данные в Git не включаются.


## Услуги, контакты, отзывы и SEO — milestone 4

- `/services/` и шесть страниц `/services/shadow/`, `/services/floating/`, `/services/light-lines/`, `/services/tracks/`, `/services/cornices/`, `/services/fabric/`: серверный текст, фотографии или подписанная иллюстрация, FAQ, контекстные обращения и связанные опубликованные проекты.
- В редакторе проекта поле «Страницы услуг» управляет связанными кейсами. Категории каталога независимы. Если связанных кейсов нет, вымышленные карточки не появляются.
- `/partners/` — сотрудничество; `/contacts/` — проверенные публичные контакты, адрес и ссылки. Источник контактов — прежний сайт клиента и карточка Яндекса, проверено 05.11.2026.
- Блок отзывов — третий на главной, после первого экрана и рассказа о подходе. Отзывы передаются официальным виджетом Яндекса без переписывания или пересказа. Высота 960 px позволяет видеть три отзыва; длинные тексты раскрываются штатной кнопкой Яндекса. Рейтинг и отзывы встроены в серверный HTML, загружаются независимо от выбора аналитики, в том числе без JavaScript. Ссылки «Все отзывы» и «Оставить отзыв» доступны всегда. Виджеты могут использовать собственные технические средства Яндекса; отказ от Метрики сайта ими не управляет.
- `SITE_URL=https://vlico39.ru` задаёт canonical, Open Graph, JSON-LD и домен sitemap. В sitemap входят публичные страницы и только опубликованные кейсы. Локальная и preview версии остаются noindex; production требует `APP_ENV=production` и явного `SITE_INDEXABLE=true`.
- ID Метрики `113716679` взят из старого сайта. Подключение требует `APP_ENV=production`, `ANALYTICS_ENABLED=true` и разрешения посетителя. Local/preview не отправляют статистику. Создать в кабинете счётчика JavaScript-цели из отчёта проверки; наличие ID не подтверждает доступ к кабинету.
- `/privacy/`, `/consent/`, `/cookies/` описывают обработку заявок, уведомления на `vlico_39@mail.ru`, Telegram и используемые сторонние сервисы. На юридических страницах указаны подтверждённые реквизиты оператора; неизвестные сведения не публикуются. Базовые сведения задаются `OPERATOR_NAME`, `OPERATOR_INN`, `PRIVACY_EMAIL`; `LEGAL_VERSION` меняется при обновлении текста или целей обработки. Изменение текста согласия автоматически меняет его контрольную сумму и повторно запрашивает выбор аналитики. Уведомление содержит только «Принять» и «Отклонить»: выбор относится к Метрике сайта, сохраняется до 180 дней и меняется через ссылку в футере. Сроки хранения заявок, журналов и резервных копий в политике отражают регламент оператора; автоматическая очистка этих данных приложением и ротация резервных копий не настроены.

Полный протокол, цели аналитики, ограничения перед запуском и команды проверки: [docs/milestone-4-validation.md](docs/milestone-4-validation.md).
